# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**MinuteMind** is a native macOS application (Swift 6.2, macOS 14+) for recording meetings, transcribing audio, and generating AI-powered meeting minutes with an integrated calendar, notes, knowledge management, and task system.

## Build & Run Commands

```bash
# Development build
swift build

# Release build
swift build -c release

# Run app directly
swift run MinuteMind

# Run all tests
swift test

# Run tests without network calls
SKIP_NETWORK_TESTS=1 swift test

# Package as .app bundle and install to ~/Applications
./Scripts/package_app.sh --install

# Create DMG for distribution
./Scripts/create_dmg.sh
```

**After every finished code change, run `./Scripts/package_app.sh --install`** once, before reporting the task as done, so the installed app in `~/Applications` always carries the latest code. Not needed for documentation-only changes. The script runs the full test suite (`SKIP_NETWORK_TESTS=1`) and a release build, so it is a heavy job: check for other busy sessions first and run it only once per task. If it fails, report the failure instead of declaring the task done. A running MinuteMind keeps the old build until it is relaunched; say so, do not quit it.

## Architecture

### Layering

```
Views (SwiftUI)
    ↓ binds to
ViewModels (@MainActor)         ← AppViewModel is the single central orchestrator
    ↓ calls into
Services (business logic)       ← AI, audio, transcription, calendar, automation
    ↓ persists via
Store (persistence layer)       ← JSON files + SQLite/GRDB
```

### State Management

`AppViewModel` (`Sources/App/ViewModels/AppViewModel.swift`) is the single `@MainActor` state container with `@Published` properties. All views receive it as an `.environmentObject`. Avoid creating additional view models unless a view is sufficiently complex and isolated.

Key transient properties for coordinating recording triggers:
- `pendingSessionTitle: String` — title to use on the next `startRecording()` call
- `pendingCalendarEvent: CalendarEvent?` — when set before `startRecording()`, the new session is auto-populated with calendar metadata and the event's project assignment

### Persistence

JSON files under `~/Library/Application Support/MinuteMind/`:
- `sessions.json` — recording sessions
- `projects.json` / `tasks.json` — projects and tasks (`Project.sortOrder`: the user's sidebar order; a long press on a project row makes the rows wiggle and drag into a new order, `ProjectsSidebarView`, `ProjectSidebarArranging.swift`; never-arranged projects come first, newest on top)
- `summary-prompts.json`: the meeting summary prompts (`SummaryPromptStore`; taken over once from the old `openai-profiles.json`, which is left on disk unread)
- `auto-record-toggles.json` — per-event auto-record opt-in (`AutoRecordStore`)
- `event-project-mappings.json` — calendar series → project assignment (`EventProjectStore`)
- `event-notes.json` — user notes linked to events or created manually (`EventNotesStore`)
- `epics.json` — epic groupings for workboard (`ProjectStore`)
- `voices.json` — learned speaker voices for cross-recording identity (`VoiceDirectoryStore`)
- `mcp-token`: bearer token for the local MCP server (`MinuteMindMCPServer`)
- `vocabulary.json`: the user's dictionary (`VocabularyStore`)
- `dictation-history.json`: every quick dictation and Claude mini task, newest first, capped at 1000 (`DictationHistoryStore`, sidebar "Clipboard", `DictationHistoryView`)
- `claude-mcp.json`: MCP config handed to Claude Code in workspace terminals (0600, contains the token)
- `claude-hooks.json` + `terminal-status/`: status hooks for workspace terminals and their per-session payloads
- `Workspaces/<project UUID>/`: per-project git repo (`ProjectRepositoryService`); `Workspaces/00000000-0000-0000-0000-000000000000/` is the General workspace for meetings processed without a project

SQLite via GRDB (`knowledge.sqlite`): the keyword search index (FTS5; no embeddings are computed) over the workspaces' `knowledge/*.md` files (`KnowledgeIndexer`, documents sourced `workspace:<repo id>/<path>`) plus notes. The files are the source of truth; the old database contents were moved into `knowledge/imported/` once (backup `knowledge.before-workspaces.sqlite`). Schema migrations live in `KnowledgeStore.swift`.

### Themes

`ThemeStore.shared` (`Sources/App/Supporting/ThemeStore.swift`, @Observable) holds the active `AppTheme` (`Sources/App/Config/AppTheme.swift`): Studio (system colours, the default and the pre-theme look), Ember, Midnight, Voltage, or Custom (a built-in base with accent, background, card and border overridden, light and dark each; text colours derived from the background). The Custom colours can be saved as named profiles (`SavedThemeProfile`, several, `mm.themeProfiles`), listed between the built-ins and Custom, edited in place when selected, renamed and deleted (falls back to Studio). `DesignSystem.Colors` are computed from it, so views using tokens follow the theme; `.themedWindow()` on every scene root sets tint, accent and base text colour; the terminal recolours on `.minuteMindThemeChanged`, with text and ANSI colours pushed to at least 4.5:1 on the theme background (`TerminalPalette`); workspace Claude sessions get theme "auto" through `claude-hooks.json`, so Claude picks light or dark from that background (OSC 11) whatever the user's own Claude theme is. Picker: Settings, Appearance (`AppearanceSettingsView`), keys `mm.theme`, `mm.themeCustom`, `mm.appearanceMode`. Many views still hard-code colours (stage 1 and 2 of the rollout cover tokens, page background, cards, speaker colours, terminal, workspace file tree); new UI should use `DesignSystem.Colors`.

### Multi-Window Pattern

The app uses multiple `WindowGroup`/`Window` scenes declared in `MinuteMindApp.swift`. Each window gets the shared `AppViewModel` via `.environmentObject`. New windows should follow this pattern. In full screen the window toolbar auto-hides (`FullScreenToolbarAutoHide`, set app-wide since SwiftUI owns the window delegates); since the system sidebar button goes with it, full screen adds a sidebar button beside Settings in the sidebar footer and, while the sidebar is hidden, a corner button at the page's bottom left (`FullScreenSidebarControls.swift`); View > Show/Hide Sidebar (Ctrl+Cmd+S, `SidebarCommands`) works everywhere, and torn-off Claude windows take no saved frame (they open in full screen too).

### Navigation (Home, project sidebar, history, Shift+Tab, Cmd+K)

The main window opens on Home (`HomeView`: a greeting and every project as a tile with its creature, General first, plus New Project, which opens the Home sidebar's sheet through `requestsNewProject`). The sidebar depends on the place: on Home and the global pages it is `ProjectsSidebarView` (Home, Inbox, All Transcripts, All Tasks, Calendar, Clipboard, General, the projects); a click on a project row or tile enters it and `ContentView` slides in `ProjectContextSidebar` (creature and name with the way back Home, the sections Overview / Workspace / Jobs, General only Workspace / Jobs, then the repo's `WorkspaceFileTreeView` with its branch row, Settings at the bottom); between two projects it crossfades. Each project remembers its section (`AppViewModel.projectTabs`, `mm.projectTabs`, Workspace before the first visit); `requestedProjectTab` is applied to the selected project at once (callers set `selectedProjectID` first). The tree's selection lives in `WorkspaceEditorState.selection`, so the sidebar tree and the editor share it; a click on a file opens it and switches to Workspace, and outside Workspace the selection is cleared so a click on the open file still switches. Projects without a creature show a Blob in the project colour, General the home companion (`ProjectAvatarView`).

The page flags (`isShowingHome`, `isShowingInbox`, ..., `selectedProjectID`) stay the source of truth; `AppViewModel+Navigation.swift` derives `currentPlace` (`NavigationPlace`, in `AppNavigation.swift`) from them and `go(to:)` sets them. `ContentView` records every change of `currentPlace` as a visit (`NavigationHistory`, browser-like, 50 places, sections count as places, deleted projects skipped when walked over). `MainWindowEventMonitor` (a local AppKit monitor, main window only, not while a sheet shows) maps mouse buttons 4 and 5 to back and forward (no Cmd+[ or swipes, by choice) and drives the Shift+Tab switcher (`ProjectSwitcherView`, Cmd+Tab style: hold Shift, Tab steps, arrows step both ways, releasing Shift enters, Esc cancels, Return enters, a click enters; names under the creatures; only starred projects and projects with a running Claude session, `switcherProjectIDs`; most recently used first, `recentProjectIDs`, `mm.recentProjects`, so one Shift+Tab returns to the previous project; leaving the app cancels it). Shift+Tab is left alone while text input has focus (`NSText`, i.e. text fields, notes and the code editor, or a SwiftTerm `TerminalView`) and when the switcher would be empty, so it keeps moving focus backwards there.

Cmd+K (taken by the same monitor before terminals and the editor see it) toggles the global search (`GlobalSearchView` over the window, Spotlight style; matching in `Supporting/GlobalSearch.swift`, pure and tested; sources and opening in `AppViewModel+GlobalSearch.swift`). It finds by name: pages, the open project's sections, Settings pages, projects, Claude sessions and the main menu's enabled commands (read when it opens, Services and alternates left out); in full text (2 characters or more): meetings by a plain scan of the transcripts in memory and the summaries read from disk in the background when it opens (no index of their own), and knowledge files through the existing FTS index (`KnowledgeStore.searchChunks`; notes left out). One row per meeting: title hit opens the Summary (or the whole transcript without one), transcript hit opens `TranscriptDetailView` filtered to the query (`initialSearch`), summary hit opens the Summary. Arrows, Return and Esc on the field as in the Task Commander; closing gives the keyboard back to the previous responder before a menu command runs.

### AI / LLM Integration

Claude is the only AI. Background jobs (summary, titles, todos, task brief, time blocks, board summary) call `AIClient` (`Sources/App/Services/AIClient.swift`), which runs the installed `claude` CLI via `ClaudeCodeService.chat` / `chatJSON` with `mm.claudeModel` (`sonnet` / `opus` / `haiku`, Settings, AI tab, `AISettingsView`). Without Claude Code these features are off (`AppViewModel.isAIAvailable`). There are no API profiles, no Ollama, no embeddings and no in-app assistant chat. `ToolExecutor` and `AgentTools` define and execute the tools the MCP server exposes.

**Agent tools available:** calendar (list/search/create/delete events), tasks (list/create/update/delete), reminders, knowledge base (commit), web search & fetch (defined, but not exposed over MCP), and **notes** (list/search/create/update/delete).

### MCP Server (local)

`MinuteMindMCPServer` (`Sources/App/Services/MCP/`) exposes the app to MCP clients on this Mac (Claude Code, Claude Desktop via `mcp-remote`) over Streamable HTTP at `http://127.0.0.1:47821/mcp`, using the official Swift MCP SDK. `MCPHTTPListener` is a minimal NWListener HTTP/1.1 server (bound to loopback) because the SDK ships no socket server. Every HTTP request gets a fresh SDK `Server` + `StatelessHTTPServerTransport`, since one SDK server rejects a second `initialize`.

Tools = `AgentToolRegistry` definitions executed via `ToolExecutor` (minus `web_search` / `fetch_webpage`) plus `MCPMeetingTools` (`list_meetings`, `get_meeting`, `rename_meeting`, `delete_meeting`, `search_knowledge_base`) and `MCPJobTools` (scheduled jobs, see below) and `MCPSharedProjectTools` (`complete_shared_project_setup`, see Shared Projects) and `MCPHelpTools` / `MCPAppControlTools` (see Help and Settings for Claude). `delete_*` tools carry `destructiveHint`. Access requires `Authorization: Bearer <token>` (token in `mcp-token`, 0600) and a localhost Host/Origin (DNS-rebinding protection). Enabled by default; configured in Settings → Integrations (`IntegrationsSettingsView`). New agent tools registered in `AgentToolRegistry` appear over MCP automatically.

### Help and Settings for Claude

Claude can answer questions about MinuteMind and act in the app over MCP. `HelpGuide` (`Sources/App/Help/HelpGuide.swift`, text in `HelpGuideContent.swift`) is the user guide: one topic per feature area, Markdown written for users, compiled into the app (the packaged .app carries no SwiftPM resource bundles). The Settings Help tab (`HelpSettingsView`) renders the same topics, and `get_help` serves them (index, one topic with its settings and current values, or a keyword search). `AppSettingsCatalog` (`AppSetting.swift` for the model) lists every user-facing setting with label, place in Settings, options and a read/write through the object that owns it (AutomationSettings, ThemeStore, CompanionAppearance, CompanionController, LaunchAtLogin, ...), repeating the side effects the Settings page performs (model downloads, starting the meeting radar); `list_settings` / `update_setting` use it. The MCP server's own switch and port are read-only there, so a client cannot cut itself off. `open_in_app` (a Settings page via `requestedSettingsTab`, a sidebar destination, a project tab) and `start_recording` / `stop_recording` live in `MCPAppControlTools` + `AppViewModel+AppControl.swift`. The server's `instructions` tell clients to call `get_help` first for questions about the app.

**Keep them current:** a change users can see (new or moved control, setting, shortcut, behaviour) updates the matching `HelpGuideContent` topic in the same commit, and a new setting gets an `AppSettingsCatalog` entry (or an `internalKeys` line when it is not a setting). `AppSettingsCatalogTests` fails for any quoted `"mm."` key in `Sources/` that is neither, and for entries pointing to missing guide topics.

**Diagnostics:** `get_app_status`, `get_app_log` and `run_repair` (`MCPDiagnosticsTools`) let Claude debug the app for the user. `AppViewModel+Diagnostics.swift` fills a `DiagnosticsSnapshot` (app build, Claude Code at launch and now, permissions via `OnboardingPermissionCheck`, Parakeet's on-disk state from `ParakeetTranscriptionService.installDiagnostics` plus progress and `parakeetLastError`, speaker models, microphone, disk, queues, failed meetings, Shared Project sync, failed job runs, `recentErrors` collected from `errorMessage`); `AppDiagnostics.issues(in:)` (`Sources/App/Help/AppDiagnostics.swift`, pure, tested) turns it into issues with severity, a fix for the user and an optional `RepairAction`. Repairs reuse the app's own paths (install/verify Parakeet, speaker models, permission request, retry transcription, Shared Project sync, index rebuild); downloads start in the background and return at once. `AppLogReader` reads this process's unified log (`OSLogStore`, current process only), where failures that are never shown (knowledge curation, model loading) end up. A failure mode the app can detect gets a rule in `AppDiagnostics` and a symptom in the guide's Troubleshooting topic (`HelpGuideTroubleshooting.swift`).

**Updates:** `check_for_update` and `update_app` (`MCPUpdateTools`) compare `CFBundleShortVersionString` with the latest GitHub release of Robschke/MinuteMind (`AppUpdateService`, tag `v<version>`) and install it by running `install.sh` as a separate bash process with `MINUTEMIND_INSTALL_DIR` set to the running app's folder: the script quits MinuteMind, replaces the .app in place and reopens it (log: `<App Support>/MinuteMind/update.log`). `update_app` refuses while recording, transcribing or processing, for development builds (no .app bundle) and when nothing is newer. The app also checks by itself (`AppUpdateChecker`): at launch and every 24 hours while it runs, and offers a newer release in `AppUpdateSheet` (release notes, Later, Update) on the main window, only while `AppViewModel.updateBlockedReason` is nil and the first-launch setup is not running (re-evaluated every minute). Later stores `mm.updateSnoozedUntil` (3 days, any version, across restarts); development builds never check. The guide topic is "updating". Releases: bump the version in `Info.plist`, write the user-facing notes to `release-notes/<version>.md` (the release body, shown in the update dialog; the script refuses without it), then `./Scripts/package_release.sh --publish` (signs with the "MinuteMind-Self-Signed" certificate, so macOS permissions survive updates; uploads `MinuteMind.zip`). After changing Swift packages run `./Scripts/generate_third_party_notices.sh`.

### Claude via Claude Code

`ClaudeCodeService` (`Sources/App/Services/ClaudeCodeService.swift`) runs the user's installed `claude` CLI headless (`claude -p`, no tools, no MCP, no settings, temp cwd) so the app uses Claude through the user's subscription without an API key. When it is installed it takes precedence: transcript cleanup (`TranscriptCleanupService`, Sonnet, 120-line chunks, 3 in parallel, structure check kept), meeting minutes (the selected summary prompt or the default prompt) and titles, with `mm.claudeModel`; knowledge curation uses it too. Knowledge extraction uses section headings as titles.

### Dictionary and Transcript Correction

`VocabularyStore` (`vocabulary.json`) holds the user's dictionary: a correct term plus the forms it is misheard as. `VocabularyCorrection.apply` replaces those forms whole-word and case-insensitively (speaker prefixes untouched). Terms feed `TranscriptionContext.extraTerms` (engine biasing and the fuzzy `ProperNounCorrection`); exact replacements run after every transcription, on each final live-transcript line and on quick-dictation text; the dictionary is also part of the cleanup prompt. Edited in Settings, Dictionary tab (`DictionarySettingsView`); Claude can use the MCP tools `list_dictionary`, `add_dictionary_entry`, `delete_dictionary_entry`.

Transcript correction before the summary always uses Claude Sonnet (`TranscriptCleanupService`); without Claude Code only the dictionary's exact replacements apply. The model never sees the blank lines between turns (`TranscriptCleanupService.textLines` / `restoringBlankLines`): trimmed answers used to fail the structure check on every chunk starting or ending on one. Measured 2026-10-13 on a 433-line meeting: Claude summary about 35 s, each extra `claude -p` start about 3 s.

### Meeting Radar and Pill

`MeetingRadar` (`Sources/App/Services/MeetingRadar.swift`) polls the CoreAudio process list (macOS 14.4+, `kAudioProcessPropertyIsRunningInput`) and reports a call when a known call app or browser holds the mic for 5 s; the call ends when the app releases the mic for 8 s or quits. It also detects screen sharing from window titles. It replaces the old Teams-only auto-start (`TeamsCallDetector` is no longer started); the header switch "Detect Meetings" (`mm.meetingRadarEnabled`, default on) controls it.

`MeetingPillController` + `MeetingPillView` show the floating pill (non-activating NSPanel, screen-saver level, `sharingType = .none`, bottom center 40 pt up): detected card, hollow ring when ignored, one-time consent notice, recording capsule, "Meeting over?" (Stop / Keep Recording, no countdown) when the call app releases the mic or on long silence, and "saved" (asks "Which project?" when it has none, see Inbox and Meeting Processing). While a screen share is detected a menu bar item mirrors every state. Countdowns pause on hover. Calendar events not opted in to auto-record are offered through the pill too. **Recordings only end when the user stops them** (2026-10-08): call end, silence and the old Teams detector only ask; the 3-hour limit is the one automatic stop. The same pill carries quick dictation (fn by default, `QuickDictationController`): a quiet idle bar is always visible while dictation or meeting detection is on, hover opens it to the dictation hint and Record, and dictating turns it into a waveform-only capsule over any meeting state that shrinks back into the bar when the text is pasted. Until the microphone delivers sound (`QuickDictationService.isMicLive`: first non-zero buffer, or 1 s of buffers; AirPods need about a second to switch to their headset profile) the bars lie flat and dimmed with a sweep, "Listening" is announced only then, the companion perks up only then, and after 3 s without sound the capsule says "Microphone not ready". `MM_PILL_DEMO` walks through these states too. Holding the hold key with Control calls the voice assistant (`ClaudeAssistantService`, 2026-10-13; fn + Control replaced the triple tap 2026-10-27), push-to-talk: it listens while held and the release of the hold key sends; Control may come first or within the 200 ms before dictation starts: the selected text of the frontmost app (Accessibility, Cmd+C fallback with the clipboard restored, `SelectionCapture`) plus app and window go along; Claude Code runs headless in `App Support/MinuteMind/Assistant` with the MinuteMind MCP tools and web search always allowed, the terminal (Bash, Read) when Settings allow it (`mm.claudeTaskAllowsTerminal`, default on, user decision), MinuteMind deletes blocked. It acts or answers and ends with PASTE (inserted when a text field has focus, else an answer card with Copy/Insert), DONE (result card) or ASK (question card; typed or dictated answer resumes the session). Runs in the background, one at a time; the companion works meanwhile; right click offers Cancel Claude Task. Open Chat in the listening capsule still opens the Claude app. Presses under 200 ms are taps and never start dictation. A double tap starts a quick recording (`startQuickRecording`, `RecordingSession.kind = .quickRecording`, title "Recording", no project, no silence auto-stop, `mm.quickRecordingEnabled`); the next press of the key stops it. Only quick recordings stop on the key: a recording started with the mouse stops only with the mouse. Presses in the first second do not stop it and quick recordings under 2 s are discarded. Design reasoning lives in the file headers and in design reviews done during development.

### Inbox and Meeting Processing

After a recording stops, transcription always runs automatically. The rest ("Process": cleanup, summary, title, todos, knowledge) only runs once the meeting has a project or was filed to General (`RecordingSession.assignedToGeneral`; pickers pass `ProjectRepositoryService.generalProjectID`), see `MeetingProcessingRule`. It starts on its own as soon as the recording has a project and a transcript, whether the project was picked before, during or after transcription; it never waits for speaker names, and quick recordings are processed like meetings (user decision 2026-10-27: after picking the project nothing else should be needed). ### Scheduled Jobs

A job is a prompt Claude runs on a schedule inside a workspace (every project and General). Files are the source of truth (`ScheduledJobFiles`): `jobs/<slug>.md` (frontmatter: title, enabled, schedule `hourly`/`daily`/`weekly`, time, until, days or day, access `read-only`/`standard`/`full`, model or `default`, notify `always`/`failures`/`never`, created, active_since; the body is the prompt) and one file per run, `jobs/<slug>/runs/<yyyy-MM-dd-HHmm>.md` (status, trigger schedule/catch-up/manual, scheduled slot, times, model, access; the body is Claude's final reply). The slug is the job id, so a title change never moves runs. `JobSchedule` does the calendar math: hourly runs every full hour from time to until, daily at time, both limited to weekdays (empty = every day), weekly on one weekday; `dueSlot` only looks at the latest slot before now, so missed slots are caught up once, and slots before `active_since` (reset on create, schedule change and switching on) never fire. `ScheduledJobStore` (@Observable, `AppViewModel.scheduledJobs`, wired in `AppViewModel+ScheduledJobs.swift`) rereads all workspaces every 30 s and on wake, queues due jobs (not in test processes, not for deleted projects, not without a prompt) and runs one at a time across all workspaces; UI edits are written after 0.6 s and committed after 4 s, MCP edits at once; commits only touch `jobs/`, files Claude changes during a run stay uncommitted. `ScheduledJobRunner` runs `claude -p` in the repo with `--setting-sources user` (the user's claude.ai connectors, such as Microsoft 365 and Slack, only load with the user settings; `""` and `--restricted` drop them), the MinuteMind MCP config and the tools of the access level: read only = Read/Glob/Grep/WebSearch/WebFetch + MinuteMind list/get/search tools + the connectors' reading tools (`--permission-mode dontAsk`, the other MinuteMind tools in `--disallowedTools`); standard = + Edit/Write (acceptEdits) + all MinuteMind tools except `delete_*` + every connector tool; full = + Bash and deletes. Since the user settings come along (their `defaultMode` may be auto, their hooks and plugins load), every run sets its permission mode, and a PreToolUse hook passed via `--settings` (`connectorGateCommand`) gates every MCP tool but MinuteMind's: connector tools by access level (read only decides by the words in the tool name, since names are only known at run time; writing words win, unknown names are denied), all other MCP servers denied. 30 min timeout, Stop cancels. Notifications (`mm.jobRun` category) follow the job's notify setting and open the run. UI: the Jobs section of every project and General (`ScheduledJobsView`: list left, `ScheduledJobEditorView` right, autosave, Run Now / Stop; a run replaces the right side, `ScheduledJobRunView`, with Open in Workspace). MCP tools: `list_jobs`, `get_job`, `create_job`, `update_job`, `delete_job`, `run_job_now`, `list_job_runs`, `get_job_run`. Jobs run only while the app runs.

### Shared Projects

A project can be a Shared Project (`Project.shared`, models in `SharedProject.swift`): its workspace repo syncs with a git remote (a private GitHub/GitLab repo) shared by several MinuteMind users; members are that repo's collaborators, and whoever shares a project first is its admin (`SharedProjectManifest.admin` in `.minutemind/project.json`). The project id is the workspace folder name, so every member's local project has the same id. The user's display name (`ContributorName`, `mm.displayName`, Settings, Integrations, "Shared Projects"; changing it keeps existing folder names) is appended to the folders they publish and listed as a member.

**Layout and publishing.** In a Shared Project `ProjectRepositoryService` mirrors published items (`RecordingSession.publication == .published`) to `meetings/` and `recordings/` as `folderName(for:) + "-" + ContributorName.folderSuffix(name)`, and everything else (nil counts as private) to `private/meetings/` and `private/recordings/` without a suffix. One mirror index per kind (`.minutemind/meetings.json`, `recordings.json`) covers both areas: entries hold the bare folder name, the area is wherever that folder exists. `ensureRepository` keeps `/private/` and both indexes in `.gitignore` (one fixed line, never per item, so the shared `.gitignore` reveals nothing) plus the index lines and `/jobs/`, untracks indexes and jobs committed earlier and creates `private/`; only tracked areas are committed. A folder under `private/` leaves it only by publishing in a Shared Project: `mirror` never moves one out while the project is still Private (the skill moves items there before the project turns Shared), keeps a folder the skill already suffixed, and such an item is curated into `private/knowledge/`. Once the shared knowledge cites a published folder (`MirrorEntry.cited`), renames no longer move it. The CLAUDE.md block gets a "Shared Project" section (members and admin, cite contributors, never edit other members' folders, `private/` and `private/CLAUDE.private.md` never copied into shared files, sync is the app's job). Publishing (`AppViewModel+SharedPublishing.swift`) is one-way: `setPublication` stores the choice (`storePublication`) and moves a mirrored item out of `private/`, retracts it from `private/knowledge/` if cited there and curates it into the shared knowledge; `publishPrivateItem` does the same for a folder under `private/meetings|recordings` (session found by index or frontmatter). A project change resets `publication`.

**Knowledge.** An item under `private/` is curated into `private/knowledge/` (not committed, still indexed: `knowledgeFiles(in:)` returns both layers); `commit_to_knowledge_base` and the assistant's save write there too in Shared Projects. A published item becomes a `.shared` curator job replayed by `SharedProjectSync.replayKnowledge`: push the item first, reset a detached worktree at `<App Support>/MinuteMind/SharedCuration/<project id>/` (outside the workspace, tracked files only, so `private/` does not exist there) to `origin/<branch>`, run `KnowledgeCurator.runStep`, commit `knowledge/` and push; a rejected push starts over (3 attempts, then a sync problem), then the main checkout is pulled. The route follows where the folder sits, so a private folder never feeds `knowledge/`.

**Sync** (`SharedProjectSyncService.swift`, wired in `AppViewModel+SharedSync.swift`): commit, fetch, `rebase --autostash` onto `origin/<branch>`, push, at launch, every 3 minutes (not in test processes), after mirror commits, after publishing and on Sync Now; only on main or master without a merge or rebase (otherwise "Switch back to main to sync"). git runs off the main thread with `GIT_TERMINAL_PROMPT=0` and never force-pushes. The commit step (`SharedSyncCommit.swift`) commits every change that is not gitignored ("Workspace changes"), except files over 50 MB (held back, `SharedSyncStatus.heldBack`, listed by "N files not synced" in the branch row with Sync anyway, remembered in `.git/info/minutemind-large-files`; above 100 MB never, GitHub refuses them) and nested git repos (skipped). A rebase conflict is aborted and resolved in memory (`SharedSyncMerge.swift`): `git merge-tree --write-tree` against the remote, per file an edit wins over a deletion, both sides deleted stays deleted, text changed on both sides is merged by headless Claude (`SharedTextMerger`, the model from Settings, answer between `<merged>` tags, refused with conflict markers); the result is written in a temporary index, committed with both parents ("Sync: merge with the other members' changes", naming the files) and pushed, and the next rebase fast-forwards. Binary or huge files, renames, file/folder clashes and a failed Claude merge stay "Sync conflict in <file>"; the working folder is never left mid-merge. A pull that brought commits reindexes knowledge. Status per project: `sharedSync.status(for:)`. Jobs are never shared: `jobs/` (definitions and run results) is gitignored in a Shared Project, so each member's jobs stay on their Mac and run there as in a Private project.

**Becoming shared and joining** (`AppViewModel+SharedSetup.swift`, git work in `SharedProjectSetupService.swift`). "Make Shared Project..." (sidebar right click; a small sheet asks for the display name first when none is set, `ContributorNameSheet`) writes the migration skill (`SharedProjectSkill.swift`) to `<workspace>/.claude/skills/share-project/SKILL.md` (excluded locally via `.git/info/exclude`), opens the Workspace tab and starts a Claude session whose first prompt (`claudeLaunch(initialPrompt:)`, passed after `--`) runs it with project id, name, colour, display name and folder suffix. The skill asks everything through AskUserQuestion (publish meetings and recordings: all, none, in batches; jobs; CLAUDE.md user text to `private/CLAUDE.private.md`; other files to `private/files/`; code repos), moves private items under `private/`, suffixes published folders and updates the indexes, splits `knowledge/` from `private/knowledge/`, writes `.minutemind/project.json` and the `.gitignore` lines, keeps the old history as the local branch `pre-share-backup` (it contains private meetings and is never pushed), starts an orphan `main`, and only after a confirmed summary creates the repo (`gh repo create --private`) and pushes `main`. It then calls the MCP tool `complete_shared_project_setup` (`MCPSharedProjectTools`), which checks origin, manifest and the pushed main (`validateSetup`: main is the only ref on origin, its history has one root commit that already holds the manifest, and no commit in it touches `private/` or `jobs/`), records each session's `publication` from the indexes (`recordPublications`) and sets `Project.shared` (`setProjectShared`). Joining (New Project sheet, Create new / Join shared, `JoinSharedProjectForm`) runs `joinSharedProject(remoteURL:)`: clone into `Workspaces/.join-<uuid>`, require the manifest, refuse an existing project id or folder, commit `Join: <name>`, move the clone to `Workspaces/<project id>`, create the project with that id (`addJoinedProject`), clone the manifest's code repos into the locally excluded `code/`, and let the sync push.

**UI.** A Shared Project shows a people mark after its name in the sidebar (`SharedProjectMark`; orange dot and the problem as tooltip on sync problems). The workspace branch row shows the sync state after the branch ("Synced 2 min ago", "Syncing...", or the problem in orange) and Sync now (`WorkspaceSharedSyncStatus`). In the file tree (`WorkspaceFileOperations.lockReason` / `dropRefusal` with `isShared: true`) `private/`, `private/meetings/`, `private/recordings/` and everything in the last two keep their name and place and take nothing in; `private/knowledge/` is locked like `knowledge/`; nothing can be dragged out of `private/` into a shared folder (`privateLeakRefusal`). A right click on a folder directly in `private/meetings/` or `private/recordings/` offers Publish... (`publishablePath`), confirmed by an alert saying publishing cannot be recalled.

### Audio Pipeline

1. `MicRecorder` → `.caf` file via `MicrophoneCapture` (an input-only Core Audio unit; AVAudioEngine fell back to the AirPods' microphone whenever they were the output), recording from the microphone chosen in Settings, Audio (`MicrophonePreference`: remembered by device UID, `mm.inputDeviceUID`, nil = System Default; never set as the system default input, so headphones connecting do not pull recordings onto their microphone and stay in their high-quality profile; quick dictation uses the same choice). Capture restarts only when that microphone moves, disappears or changes its rate (a new rate is converted into the file's), and says "Recording continues with X" only when the microphone really changed. Also computes per-buffer RMS exposed as `currentLevel: Float` for silence detection. After recording stops, the `.caf` is converted to `.m4a` (AAC) for storage efficiency (~30x smaller).
2. `SystemAudioRecorder` → `.caf` via ScreenCaptureKit (16 kHz mono PCM, requires Screen Recording permission). Also converted to `.m4a` post-recording.
3. Recordings have a **3-hour maximum duration** — auto-stop with 10-minute warning.
   **Audio retention:** `AudioRetentionPolicy` deletes a recording's audio (transcript, summary and session stay) 14 days after it was made, unless the card's "Keep audio" checkbox (`KeepAudioToggle`, `RecordingSession.keepAudio`) is ticked. Recordings without a transcript, active ones and queued ones are never purged. `AppViewModel.purgeExpiredAudio()` runs at launch and every 6 hours.
4. `AudioProcessor` → waveform data, audio mixing, speech activity detection, M4A conversion
5. Speaker diarization engines (`SpeakerDiarizer` protocol): `Nemotron3SpeakerDiarizer` (NVIDIA Nemotron 3 via FluidAudio >= 0.17.4, up to 8 speakers, `mm.diarizationEngine = "nemotron3"`, the default, own install marker; used only once installed) or `FluidAudioDiarizer` (the fallback until then, and `fluidAudio`). The onboarding installs Nemotron and switches diarization on. Nemotron gives no embeddings, so voice-library vectors still come from the WeSpeaker extractor and `voices.json` stays compatible. Opt-in smoke test: `MM_DIARIZATION_SMOKE_FILE=<audio> swift test --filter DiarizationEngineSmoke`.
6. Transcription options:
   - `ParakeetTranscriptionService`: NVIDIA Parakeet Ultra (a post-training of TDT v3, same 25 languages, lower error rates) on-device via FluidAudio, the default (must be installed first via Settings → Automation; the marker `parakeet-installed.json` stores version, folder and Hugging Face commit). Settings checks the model's Hugging Face repo for a newer commit (`checkParakeetUpdate`); Update downloads it pinned to that commit into its own folder (`FluidAudio/Models/minutemind-parakeet/<sha>/`) and switches once complete, older folders are pruned at the next launch. An existing v3 install (old marker `parakeet-tdt-v3-installed`) keeps working and is offered Ultra as the update. A new model family needs a FluidAudio and code update, not the button.
   - `TranscriptionService`: Apple Speech framework (on-device, free), the fallback while Parakeet is not installed; live dictation always uses it
   These are the only two engines (`mm.defaultTranscriptionModel` = `parakeet` / `appleSpeech`; any other stored value is reset to `parakeet` at launch).

**Transcription Queue:** `TranscriptionQueue` (`Sources/App/Services/TranscriptionQueue.swift`) is a `@MainActor ObservableObject` that serialises all transcription jobs. Views call `AppViewModel.enqueueTranscription(sessionID:model:runPipeline:)` instead of the raw `transcribe*` methods. Jobs process one at a time to avoid GPU/CPU contention. When `runPipeline` is true, minutes generation, title generation, and todo extraction run automatically after transcription succeeds. The queue exposes `@Published` state (`jobs`, `currentJob`, `pendingCount`, `activeCount`) for UI indicators in the sidebar and status area.

**Audio Import:** `AudioImportService` (`Sources/App/Services/AudioImportService.swift`) turns an existing audio file into a normal session. Entry points: dropping files onto the transcripts list in `AllTranscriptsView`, or **File → Import Audio…** (⌘I) which opens an `NSOpenPanel`. `AppViewModel.importAudioFiles(_:)` copies each file into the recordings folder (never references it in place — Voice Memos hands out temporary container paths), stores it as the session's **microphone** channel so waveform/transcription/cropping/export all work unchanged, creates the session with status `.recorded` and the current `pendingProjectID`, then generates the waveform. Transcription is deliberately *not* started automatically — the user hits transcribe on the card.

### Speaker Identity (Voice Library)

`FluidAudioDiarizer` returns a `DiarizationResult` (turns + a voice embedding per cluster). `SpeakerLabeler` records `embeddingByLabel` while numbering clusters, `SpeakerSampling.samples` attaches those embeddings and each speaker's total talk time to the `SpeakerSample`s, and they end up on `RecordingSession.SpeakerProfile`.

`VoiceDirectoryStore` (`voices.json`) holds `KnownVoice` entries — name + averaged L2-normalized embedding. After transcription, `AppViewModel.recognizeSpeakers(in:samples:)` matches each detected speaker against the library (cosine distance ≤ `VoiceEmbedding.matchThreshold`, stricter than FluidAudio's within-recording threshold) and rewrites the transcript to use the known names before it is stored or exported. One voice can only claim one speaker per recording — ties go to the closer match.

`AppViewModel.renameSpeakers(_:for:)` feeds names back into the library, so naming a speaker once makes every later recording recognize them. Auto-matched profiles carry `wasAutoMatched`, which `SpeakerNamingSheet` shows as a "Recognized" badge. `VoiceLibrarySettingsView` (inside the Automation settings' speaker section) lists, renames, and deletes learned voices.

### Calendar Integration

`CalendarService` (EventKit wrapper, `@MainActor`) fetches `CalendarEvent` value types from the system calendar. `CalendarEvent` includes:
- `id` — `EKEvent.eventIdentifier` (unique per occurrence)
- `seriesId` — `EKEvent.calendarItemExternalIdentifier` (shared across recurring series; nil for non-recurring)
- `isRecurring` / `seriesKey` — used as the key for `EventProjectStore`
- `participantStatus` — current user's acceptance status (accepted/declined/tentative/pending/unknown), derived from `EKParticipant.isCurrentUser`

`CalendarView` shows a sidebar event list + `WeekCalendarView` (Apple Calendar–style week grid). Clicking an event opens `CalendarEventDetailView` as a resizable sheet (`.resizableSheet()` modifier patches `NSPanel.styleMask` to include `.resizable`).

### Event → Project Assignment

`EventProjectStore` maps `CalendarEvent.seriesKey → project UUID`. Assigned in `CalendarEventDetailView` (a folder picker below the date/time row). When set for a recurring series, **all occurrences** share the same key, so every recording auto-routes to the correct project. `AppViewModel.startRecording()` reads `pendingCalendarEvent` and applies the mapping to the new session's `projectID`.

### Project Export (Transcripts & Summaries)

`ProjectExportService` (`Sources/App/Services/ProjectExportService.swift`) files new transcripts and AI summaries into a per-project folder configured in the Project Settings sheet (`ProjectSettingsSheet.swift`, opened from the project header menu). Structure: `<export folder>/<yyyy-MM-dd>/<meeting name>/transcript.txt` + `summary.md`. Re-runs never overwrite — they write `-v2`, `-v3`, … siblings (identical content is skipped). The meeting folder (relative path) is persisted as `RecordingSession.exportFolderName` so re-exports and title renames (AI title generation, manual rename) keep targeting/renaming the same folder.

**Project selection at record time**: the picker next to the record button sets `AppViewModel.pendingProjectID` (persisted; calendar triggers use the event's project mapping instead). No project → the recording starts and is stored as before, just without file export. `startRecording()` refuses to start only when the resolved project has neither an export folder nor the explicit opt-out (`Project.exportOptOut`). Live dictation bypasses this via `startRecording(requiresProject: false)`.

### Automation / Background Scheduler

`AutomationCoordinator` (Swift actor, `Sources/App/Supporting/AutomationCoordinator.swift`):
- **Event monitor loop** (every 30 s): fetches events in a ±60 s window, skips all-day and declined events, checks `AutoRecordStore`, sets `pendingCalendarEvent` + `pendingSessionTitle`, calls `startRecording()`. Triggered event IDs are persisted to UserDefaults with 2-hour pruning.
- **Silence detection loop** (every 5 s): polls `AppViewModel.currentCallLevel` (mic and system audio). When cumulative silence ≥ `autoStopSilenceThreshold` the pill asks "Meeting over?"; it never stops the recording.
- **Auto-pipeline**: after a recording stops, runs transcription (model from `AutomationSettings.defaultTranscriptionModel`), then `generateMeetingMinutes` if `autoPipelineEnabled`. Summary-ready notification fires via `UNUserNotificationCenter`.

`AutomationSettings` (`Sources/App/Config/AutomationSettings.swift`) — `@AppStorage`-backed settings: `autoStartEnabled`, `autoStopSilenceThreshold`, `autoPipelineEnabled`, `defaultTranscriptionModel`.

### Notes System

`EventNote` (`Sources/App/Models/EventNote.swift`) — a user note with:
- `eventId: String?` — links to a calendar event (nil = manually created note)
- `isManual: Bool` — computed from `eventId == nil`
- `projectId: UUID?` — optional project link
- `content`, `tags`, `eventTitle`, `eventDate`

Notes are created in `CalendarEventDetailView` (per-event) or over MCP. `ProjectNotesTabView` (no longer shown in projects) provides keyword search, tag filtering with click-to-filter chips, sort, and a resizable detail sheet (`NoteDetailSheet`) with editable title for manual notes, tag drag-and-drop reordering, and a delete button with confirmation.

`AppViewModel` note methods: `note(for:)`, `upsertNote(_:)`, `createManualNote(projectId:)`, `notesForProject(_:)`, `deleteNote(_:)`.

### Workboard (Kanban Board)

`ProjectDetailView` shows 3 sections, chosen in the project's sidebar: **Overview** (the project's tasks and recordings), Workspace and Jobs (see Scheduled Jobs). The Board and Notes tabs were removed from the UI; their views (`WorkboardView`, `ProjectNotesTabView`), data (`epics.json`, `event-notes.json`) and MCP tools remain. A stored tab that no longer exists opens Overview.

**Data model extensions:**

- `Project` has optional `startDate`/`targetDate` for timeline tracking.

**Key views:**

- `WorkboardCardView` — compact task card with priority strip, epic tag, due date pill

**Agent tools:** `list_project_epics`, `create_project_epic`, `get_board_summary`. Task tools (`create_project_task`, `update_project_task`) also accept `status` and `epic_id` params.

### Onboarding (first-launch setup)

A new install (no projects, no recordings, no Parakeet model) opens on `OnboardingView` in place of the main window's sidebar and page (`ContentView`); existing installs are marked done the first time a build with it runs (`mm.onboardingCompleted`), and Help > Show Welcome Tour opens it for anyone. `OnboardingFlow` (singleton, `Sources/App/Supporting/OnboardingFlow.swift`) holds the steps and stores the current one (`mm.onboardingStep`, so quitting halfway resumes there): Welcome, one page per permission (`OnboardingPermissions.swift`: Microphone, Screen & System Audio Recording, Accessibility, Calendar, Notifications, Speech Recognition; each skippable, polled every second; screen recording counts as pending until the restart), Claude (`OnboardingClaudeSetup`: finds the CLI uncached via `ClaudeCodeService.findBinary`, shows the install command when missing, and one click registers the MCP server in Claude Code's user scope with `claude mcp add --scope user`, replacing an older `minutemind` entry), the speech models (Parakeet, then Nemotron 3; the download runs on while the tour plays and afterwards switches diarization on with Nemotron), three tour cards (the dictation / Claude key, the companion with the animated creature, projects with the Shift+Tab switcher and the Cmd+K search; `OnboardingTourPages.swift`, the keys drawn as key caps, the dictation keys read from the setting) and Finish: what is still missing, then Restart MinuteMind (waits for running downloads, relaunches through a small shell that waits for the old process, opens on General via `mm.onboardingSelectGeneral`). Only a rerun may close without restarting. The General workspace repo is created at every launch (`AppViewModel+Onboarding.swift`) and the sidebar shows General even before the first project. Page snapshots for checking the layout: `MM_ONBOARDING_SNAPSHOT_DIR=<folder> swift test --filter Onboarding`.

### Settings

One window (`Window("Settings", id: "settings")`, `MeetingMinutesSettingsView`), opened by the gear row at the bottom of the sidebar (`SidebarSettingsRow`) and the app menu's Settings… (Cmd+,, `OpenSettingsButton`, both in `Sources/App/Components/OpenSettingsButton.swift`); it is not listed in the Window menu. The Automation tab starts with Startup: "Open MinuteMind at login" (`LaunchAtLogin`, `SMAppService.mainApp`, state read from macOS so it matches System Settings, Login Items; switched on once at the first launch of a build that has it, `mm.launchAtLoginInitialized`, because jobs and meeting detection only run while the app is open).

Tests live under `Tests/` and use the Swift Testing framework. Use `@Test` functions with `#expect`/`#require` macros. Set `SKIP_NETWORK_TESTS=1` to skip tests that hit external APIs (web search).

## Key Patterns & Gotchas

- **Resizable sheets**: SwiftUI `.sheet()` on macOS uses `NSPanel` with no `.resizable` in its `styleMask` by default. Apply `.resizableSheet()` (from `ResizableSheet.swift`) to sheet content to enable user resizing.
- **CalendarService is `@MainActor`**: `fetchEvents(from:to:)` must be called on the main actor. The `AutomationCoordinator` actor uses `await MainActor.run { ... }` for all CalendarService access.
- **`pendingCalendarEvent`**: set this on `AppViewModel` before calling `startRecording()` to attach calendar metadata and auto-assign the project. It is cleared inside `startRecording()` after use.
- **Debug demos (DEBUG builds only)**: `MM_PILL_DEMO=1|visible` cycles the pill states (`visible` lets screenshots capture it), `MM_WORKSPACE_DEMO=<project UUID>` opens that workspace in a window, `MM_INBOX_DEMO=<days>` opens the Inbox counting the last N days, `MM_SETTINGS_DEMO=dictionary|automation` opens that settings page in a window. Do not run a debug build while the installed app is running: both would write the same JSON files.
- **EventNote upsert**: manual notes (nil `eventId`) are matched by `id`; calendar-linked notes are matched by `eventId`. This allows multiple manual notes per project.
